# doze-aws compatibility

What doze-aws does of each AWS API it answers, measured, not claimed:

- **Built** counts the operations in AWS's own model of the API that this build serves. The rest are refused by name (HTTP 501, header `X-Doze-Not-Built`), never answered wrongly.
- **Matches AWS** is how many recorded checks give exactly the answer real AWS gave when the same calls were made against an AWS account (status, error code, message and response shape, after removing ids and times). *Not yet recorded* checks exist in the test suite but have not been run against AWS yet.
- Every operation not built is listed below as *planned* or *not planned*, with the reason.

## Everywhere

- Requests are not signature-checked by default (`--auth trust`): any access key works, as with most local AWS tools. `--auth verify` checks every SigV4 signature against the configured key and the keys IAM issues.
- IAM refusals are logged and let through by default (`--iam soft`), so a missing permission is a warning in development rather than a failure. `--iam enforce` refuses as AWS does; `--iam off` skips evaluation.
- One account (`--account`, default 000000000000) and every region, each region kept apart on disk.
- Nothing leaves the machine unless a target says so: SMS, email and mobile push are accepted and sent nowhere; HTTP(S) subscriptions, API destinations and webhooks are really called.
- CloudFormation makes the resources of the services doze-aws runs. A resource of a service it does not run (Cognito, ECS, AppSync, load balancers...) is not created: the stack carries on, the resource reports CREATE_COMPLETE with a status reason saying so, and a warning is logged.

Differences from AWS, on purpose:

- VPC links are kept and follow AWS's status lifecycle without the wait (`PENDING` when made, `AVAILABLE` when next read). There is no VPC locally: an integration with `connectionType: VPC_LINK` calls its integration URI directly, so point it at a local address.

- Usage plans meter and enforce: the quota per key and the throttle as a token bucket per key (429 `Limit Exceeded` and `Too Many Requests`). `GetUsage` is current at once (AWS reports after a delay). Per-method throttles in a plan's stages, and the account-level throttle, are not enforced.

Differences from AWS, on purpose:

- Metric math is worked out in `GetMetricData` and in metric math alarms: arithmetic, comparisons and logic, `ABS CEIL FLOOR LOG LOG10`, `AVG SUM MIN MAX STDDEV`, `DATAPOINT_COUNT`, `PERIOD`, `TIME_SERIES`, `IF`, `METRICS`, `REMOVE_EMPTY FIRST LAST SORT SLICE`, `FILL RATE DIFF DIFF_TIME RUNNING_SUM`, the time functions and `SEARCH`. - `ANOMALY_DETECTION_BAND` is a statistical stand-in, not AWS's trained model: the mean of the metric's datapoints in the window read (for an alarm, its window and up to 50 periods before it), plus and minus the given number of standard deviations.
- `SEARCH` matches a partial term as a case-insensitive part of a namespace, metric name or dimension; AWS matches on the words of a name. A search finds a metric as soon as it has data; AWS can take minutes to index a new one.
- Log alarms (`PutLogAlarm`) run their Logs Insights query on its `rate()` schedule against the local CloudWatch Logs and are judged M out of N on the results. A run with several contributors (`... by host`) counts as breaching when any contributor does: contributors are not judged one by one, and `PARTIAL_DATA` is never reported.
- Composite alarms are judged on their rule as soon as they are made and whenever an alarm they name changes. `ActionsSuppressor` is kept and shown but never suppresses an action. Deleting an alarm that a composite names is accepted; the composite then finds it in no state.

Not planned: Datasets, vended-metric configuration, OpenTelemetry enrichment, managed Contributor Insights rules, alarm contributors and rendered graph images: features of AWS's own console and services, with no local use yet. ## CloudWatch Logs

**69 of 118 operations built.** 107 of 111 recorded checks match AWS exactly (4 differ in behaviour); 0 not yet recorded. Scored 2026-11-19.

Differences from AWS, on purpose:

- Events older than 7 days are removed (`--logs-retention-days`, 0 to keep them as AWS does), and a log group keeps at most 100,000 events (`--logs-max-events`). Local logs grow fast; this keeps the disk in check.
- Logs Insights runs the Logs Insights query language (CWLI) only: OpenSearch SQL and PPL, the `SOURCE` command and the `pattern`, `diff`, `anomaly`, `filterIndex`, `unnest` and `lookup` commands are refused with a sentence. `pct` is exact (AWS estimates). Queries and their results are kept in memory, the newest 200 queries and at most 1,000,000 result rows: a restart forgets them (AWS keeps results for days).
- A sort that is not followed only by `limit`, `fields` or `display`, and a stats command, hold at most 1,000,000 rows or groups; past that the query fails and says so.
- Field indexes change no answer and no cost locally (every event in range is read): policies are checked and kept, `DescribeFieldIndexes` reports when each indexed field was first and last seen, and `estimatedRecordsSkipped` stays 0.
- An export task runs before `CreateExportTask` answers (AWS runs it in the background), so it is `COMPLETED` or `FAILED` when first described; a bucket S3 cannot write to refuses the call.
- Destinations are one account's: the access policy is checked as JSON, kept and not evaluated. A subscription filter to a destination of the same region delivers to its Kinesis stream; a Firehose target is kept and not delivered.
- Transformers: `parseCloudfront`, `parseRoute53`, `parsePostgres` and `parseToOCSF` are refused (their logs are vended by AWS services that do not run locally); `dateTimeConverter` reads English month and day names only.
- Scheduled queries run on their schedule and write their answer to the local S3 as JSON rows; a lookup-table destination is refused.
- Logs Insights results carry doze-aws's own `@logGroupId` and pagination tokens, and a stream id built as AWS builds it from the group id, a hash of the stream name and its creation time; AWS's are its own. `DescribeQueries` shows the caller doze-aws knows (the local keys' principal) as `userIdentity`. Live Tail delivers an event as soon as it is written, and an export task includes events written just before it (AWS may take a minute for both).

Not planned: Large log objects exist only for logs ingested through OpenTelemetry (PutOpenTelemetryLogs), which this model and doze-aws do not have; there is never an object to fetch. (`GetLogObject`)

Not planned: Data sources are named by AWS-vended logs and CloudWatch pipelines, which do not exist locally; GetLogGroupFields answers the same question for a log group. (`GetLogFields`)

Not planned: Vended logs: delivery of logs AWS services emit about themselves, which do not exist locally. (`CreateDelivery`, `DeleteDelivery`, `DeleteDeliveryDestination`, `DeleteDeliveryDestinationPolicy`, `DeleteDeliverySource`, `DescribeConfigurationTemplates`, `DescribeDeliveries`, `DescribeDeliveryDestinations`, `DescribeDeliverySources`, `GetDelivery`, `GetDeliveryDestination`, `GetDeliveryDestinationPolicy`, `GetDeliverySource`, `PutDeliveryDestination`, `PutDeliveryDestinationPolicy`, `PutDeliverySource`, `UpdateDeliveryConfiguration`)

## DynamoDB

**49 of 58 operations built.** 181 of 184 recorded checks match AWS exactly (3 differ in behaviour); 0 not yet recorded. Scored 2026-11-19.

Differences from AWS, on purpose:

- Tables, indexes and streams become ACTIVE at once (AWS takes seconds); `--dynamodb-create-ms` and friends add AWS-like delays.
- A table's stream has one shard.
- Continuous backups are always on; point-in-time recovery keeps a day of history (a bounded change log, so the disk does not fill with five weeks of every write), whatever `RecoveryPeriodInDays` says. `EarliestRestorableDateTime` reports the window that can really be served; `LatestRestorableDateTime` is the present (AWS: about five minutes ago).
- Backups, restores, exports and imports are finished when the call answers (AWS takes minutes); the answer still says `CREATING` or `IN_PROGRESS`, as AWS's does, and the next describe says `AVAILABLE`, `ACTIVE` or `COMPLETED`.
- An export writes one data file (AWS writes one per partition) in AWS's layout (`AWSDynamoDB/<id>/manifest-summary.json`, `manifest-files.json`, `data/*.json.gz`). `FilterSpecification` on an export and `ZSTD` input on an import are not built and are refused by name; an import's failed items are counted, not written to CloudWatch Logs.
- Resource policies apply at once (AWS: eventually). IAM weighs them with every request on the table, its indexes and its stream; a key IAM did not issue is the account root's and is allowed everything locally, so a deny in a resource policy binds IAM users and roles.
- A Kinesis streaming destination is sent each change after the call answers, one table to one active stream at a time; the record's partition key is the item's partition key value.
- AWS gives a new on-demand table's stream several shards (4 when recorded); doze-aws gives it one, so `DescribeStream` lists one shard.
- A restore time outside the restorable window is refused with AWS's words; the window it names is doze-aws's own (a day of history), so the times differ from AWS's.

Not planned: Global tables version 2017.11.29, superseded by replicas on the table itself; one machine has no second region to replicate to. (`CreateGlobalTable`, `DescribeGlobalTable`, `DescribeGlobalTableSettings`, `DescribeTableReplicaAutoScaling`, `ListGlobalTables`, `UpdateGlobalTable`, `UpdateGlobalTableSettings`, `UpdateTableReplicaAutoScaling`)

Not planned: Vector search over a table is new and not yet in use by the local-development tools doze-aws serves. (`SearchVectors`)

## Lambda

**79 of 88 operations built.** 90 of 91 recorded checks match AWS exactly (1 differ in behaviour); 0 not yet recorded. Scored 2026-11-19.

Differences from AWS, on purpose:

- Functions run as processes on this machine with the runtime's own interpreter (python3, node, ruby...), not in containers. Container-image functions are stored and cannot be invoked.
- Event source mappings poll SQS, Kinesis and DynamoDB Streams.
- Durable functions run with AWS's durable execution SDKs unchanged: checkpoints, replay, waits, step retries, callbacks, child contexts, map and parallel, chained invokes. - A durable invocation that fails without an answer from the SDK (a crash, a timeout) is tried three times, one and two seconds apart, before the execution fails; AWS's retry policy for these is not recorded.

- Durable execution error messages that AWS's own local checkpoint server (`@aws/durable-execution-sdk-js-testing`) does not state are doze's words, not recorded ones.
- A durable execution's X-Ray trace header is doze-aws's own id in X-Ray's format; the last invocation ends at the instant the execution does (AWS reads the two times apart).
