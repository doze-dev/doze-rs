## PART 1. The Go console that exists today

### 1.0 Shape

- `console/` in `doze-kafka`: server-rendered Go (`html/template`), htmx + Alpine + CodeMirror 6 vendored, embedded in the binary (`console/console.go` header).
- It is a real Kafka client (franz-go over loopback/unix socket, `console/backend.go`), authenticating like any client when SASL is on. Everything the Kafka APIs can answer comes through Metadata, DescribeConfigs, ListOffsets, OffsetFetch, Fetch, Produce, CreateTopics etc.
- Beyond the wire, the broker hands the console five injected Go interfaces (`Options` in `console.go`): `TrafficSource` (the recorder), `GroupInspector` (coordinator memory), `LogSource` (cleaner state), `DockSource`, `ClientMetricsSource` (KIP-714), plus `BrokerFacts` (node name, data dir, SASL mechanisms). Implemented in `internal/consolefeed/{feed,groups,logs}.go`. Each is nil when the console runs apart from the broker, and the pages then say what they cannot see.
- Sizes: 14 templates, 3,264 lines (`console/templates/*.html`). Route table `console/routes.go`: 64 rows (41 GET including static/redirect/home/bare, 23 POST of which 5 are read-only previews/checks that "send nothing"). Each row carries `Mutates`, the spec that drives it, and a note; `Routes()` is exported to the e2e route gate (`e2e/route-gate.ts`, `e2e/route-gaps.txt` is empty).
- Polling (htmx/`shell.js` `data-live`): Traffic 2.5 s (`traffic.html:113`), Groups list and group detail 3 s, Topics list 5 s, topic tape (polled partial, `/topics/{name}/tape`), rail counts and heartbeat (`/api/counts`), trace job while running. Not "3 to 5 s" uniformly: Traffic is 2.5 s.
- Design lineage: the console was built to a design artifact of about 100 boards (`https://claude.ai/artifact/DFbFCyDEEbRsyFP7DRQuvx`, copied to `e2e/design/boards/*.dc.html`: Sy-01..08 shell, Tp-01..30 topics, Gr-01..18 groups, Sc-01..18 schemas, Traf-02..12 traffic, Ac, Cl, Tc, Main). `e2e/design/` is a gate that renders each board and the live page and diffs them element by element with an allow-list (`e2e/design/README.md`). This is the Kafka equivalent of the "compare built console with dream boards" rule.
- E2E: `e2e/tests/` has 34 specs (256 `test(` occurrences). It boots the real binary on its own ports with a seeded broker (`e2e/seed`), including a second "identity" mode (random port, odd prefix, data dir with a space, SASL+TLS). Specs: a11y, a11y-traffic, access, access-create, compose, console-errors, design, disconnected, dock, editor, groups, groups-boards, harbour, inspector, keyboard, keys, live, long-names, message-inspector, messages, narrow, routes, schemas, settings, shell, smoke, strip, time, topics, topics-boards, topics-boards2, trace, traffic, traffic-boards. The Rust plan makes this suite the Phase 9 gate "passes unchanged in external mode" (`doze-rs-debt/docs/port/PLAN.md`, Phase 9), so the Playwright suite is a DOM contract on any new console unless the owner changes that.

### 1.1 Shell (every page)

`templates/layout.html`: top bar (brand "z doze-kafka", workspace label, ⌘K palette button, broker address pill that shows connection state, Kafka-compat pill, theme switch system/light/dark/high-contrast), a left rail in three groups, a right-hand **inspector** panel that is part of the page (message, request, client, group member, subject, transaction, group event: `inspector.go`, `?open=kind:key`), a keys strip at the foot (`keys.go`: one declared key map drives shell.js, the "?" help overlay, the strip and the palette), a styled confirm dialog, toasts.

Rail: **Observe** (Traffic, Trace), **Data** (Topics, Groups, Schemas), **Broker** (Access, Cluster), then "Connect an app". Rail counts are live (`/api/counts`). Schemas shows "off" with a reason when the registry is not running (Sc-14).

Palette (`/api/palette`, `apiPalette` in `console/handlers.go`): jump to a topic/group/subject or act. Host guard against DNS rebinding (`hostguard.go`, `internal/hostguard`).

### 1.3 The traffic recorder and inspector

Two parts, both named in the task as "reflection-based, ~2.1k lines":

1. **Producer side, in the broker** (not the console): `internal/protocol/facts.go` (595), `summary.go` (750), `factsauth.go` (132), `observe.go` (209), `errors.go` (254). Uses `reflect` over decoded `kmsg` request/response structs to build, once when the row is made, a one-line summary per API and a `Facts` bundle (acks, per-partition results, a decoded-fields text). Header comment `facts.go`: "Never record bytes, never a header value, never a secret. Every byte slice is reported as its length... a configuration value whose name says it is a secret is hidden." 
2. **Recorder** `internal/traffic/traffic.go` (1,121 lines) + `story.go` (222): bounded in-memory ring.
3. **Renderer** in the console: `console/traffic.go` (1,370), `traffic_inspect.go` (698), `traffic_story.go` (436), `templates/traffic.html` (325), `traffic_inspector.html` (161).

Recorded per request (`TrafficEvent`, `console/traffic.go`; `traffic.Event`): row id and sequence; connection id; first/last time and count (folded repeats); remote address, **client id**, **client software** (from ApiVersions), **principal**; API name, key, **version**, kind (produce/fetch/groups/admin); correlation id; topics (max 20 / 1 KiB, rest counted); group, via-group, transactional id, detail; partitions text and generation; auto-create flag on Metadata; **error name and code and class** (`expected`, `refused`, `denied`, `not-implemented`, `failed`); **closed** (the broker closed the connection because of this request, and why); duration; request and response bytes; facts: acks, up to 16 per-partition results (topic, partition, base offset, records, bytes, error code), decoded fields text (<= 1 KiB); up to 64 ticks of a folded row (time, duration, class).
Also: per-connection state (`TrafficClient`: open/last time, requests, groups, txn id, produces/fetches/asked-telemetry flags, 1 m / 5 m request and error counts, error streak) and per-group events (`TrafficGroupEvent`: kind, member, generation, detail, member count, **cause** phrase) used for the rebalance story.
Error semantics (`internal/protocol/errors.go`): `errorTable` has a row for every error the broker returns, with class, usual cause and fix text, enforced by a test that walks `internal/broker` (`TestEveryErrorTheBrokerReturnsHasARow`). The console's single vocabulary for "no" is `refusal.go`: Refused (real Kafka would too), Denied (ACL/login), Not implemented, Failed; plus "expected" (normal flow, e.g. MEMBER_ID_REQUIRED) that is shown but not counted.

Retention (all constants in `internal/traffic/traffic.go` header): 2,000 rows; strings clipped (128 name, 256 text, 64 remote); 64 ticks per folded row; fold window 10 min; 200 events per group, 100 groups; per-connection and whole-broker counters of 61 buckets of 5 s (5 minutes). In memory only, restart empties it, "the console never sees the package" (it gets the interface). Weight rationale in header: a 900 KiB join reason once cost 1.8 GiB (TRF-1).
Not recorded: request bodies, record bytes, header values. So there is no replay of a request body; "resend" works on a stored record read back from the log, not on the captured request.

### 1.4 Rough edges seen in the templates and handlers (verified by reading, not by running)

1. Hard-coded copy that is a claim: `cluster.html` "One broker. No replication, no controller quorum. That is the whole point." and the "What this broker is not" pills (replication factor reported as 1, no leader election/no ISR, no KRaft/no ZooKeeper, not durable against disk loss). Only "single node" is conditional on the broker count. "Registry ... built in" is also literal. True for this build, but not derived from data, and "not durable against disk loss" is a static sentence whatever the fsync policy.
2. Refresh intervals typed into copy: "refreshes every 3 s" (`groups.html:86,207,214`), "retries every 5 s" and "tries again every 5 s" (`traffic.html:28,159`) are literals next to `data-live-ms` values (3000, 2500, 5000). They can drift from the real intervals.
3. Unbuilt pages are referenced in comments but not in the UI: Cluster Limits/Storage/Compaction/Listeners (Cl-03, Cl-04, Cl-07..09: `handlers_cluster.go` says they "need facts the broker does not hand the console"); per-language Connect pages (Cn-02..07: `connect.html` header). The Cluster home therefore cannot show the cleaner's state (comment `handlers_cluster.go`: "the background cleaner's own status has no source: CLU-24"); "Compacted partitions" is derived from topic configs only.
4. `LogSource` (cleaner state) is nil in the embedded module: "The embedded module and any console for a broker in another process leave it nil, and the page says so" (`logsource.go`). So the compacted-topic card often reports that the console cannot see the cleaner. Totals reset on restart (said in the code).
5. Rail uses two-letter text chips (`TR`, `TC`, `TP`, `GR`, `SC`, `AC`, `CL`, `⇢`) instead of glyphs, and the same chips appear inside the neighbours sentences (`layout.html` "ri", "neighbours").
6. `docs/console.md` still says the console is "on by default at http://kafka.<name>.doze" and is "a client of the broker over the Kafka wire protocol". The Rust plan removes .doze names for doze-kafka and reads the broker in-process, so this page of docs will be wrong for the Rust edition.
7. Several "written by" answers depend on the recorder still holding the row (2,000 rows): `handlers_topics.go:269` note "Written by is ..." says as much; a record older than the ring has no writer. The compose callout says the console's own requests are left out of Traffic.
8. Features that exist in the data but have no UI: no delete-ACL, no transaction abort, no member removal, no way to see the cleaner when the module is embedded, no registry requests in Traffic (the dock reads the registry's own log, `dock.go` `registryDock`; `trafficDock` returns nothing for a subject).
9. Tests/mutation baseline are heavy (`survivors1..6_test.go`, `console/*_edges_test.go`, 500+ survivors triaged): the Go suite's size is called "a warning, not a model" in `doze-rs-debt/docs/port/PLAN.md` quality rule 10.

## PART 2. What the Rust broker could feed a console

State of the Rust tree (`~/Code/doze-dev/doze-rs-debt`, branch `debt`): crates `kafka-wire`, `kafka-storage` (67 files), `kafka-meta` (19), `kafka-broker` (143), `kafka-server` (9), `kafka-registry` and `doze-kafka` (stubs / small), `kafka-console` is **one line**: `//! The web console: axum, maud components, view-models, traffic recorder.` with dependencies on `kafka-wire` and `kafka-broker` only. Phases 0 to 7 are built (7 awaiting audit, `docs/port/phase7.md`); Phase 8 (TLS, SASL, ACLs) and 10 (registry) are not: `broker.rs` lists `DescribeAcls/CreateAcls/SaslHandshake...` among the unserved APIs; `kafka-registry` has no source of substance.
The plan: "The console reads the broker through a direct in-process handle, not a Kafka client over loopback" (`docs/port/PLAN.md`, Context) and "typed view-models rendered by maud... Updates stay as htmx polling every 3s" (design table).

**The central fact:** almost everything below exists as private state. `kafka-broker/src/lib.rs` exports only `Broker`, `Config`, `Defaults`, `BrokerError`, `Listener`, `Outcome`; `mod partitions`, `mod groups`, `mod txn`, `mod producers`, `mod configs` are private and their types are `pub(crate)`. `Broker` fields are `pub(crate)` (`broker.rs`). A console crate therefore needs a deliberate read-only "inspect" surface on `Broker` (and `LogReader`) first. That surface is itself new work, and it is the right place to apply "weight is a feature" (build views lazily, on request).

### 2.2 What Phase 7 makes visible that Kafka consoles never show

The commits `ac795b7..9eded61` ("Phase 7d") and `docs/port/phase7.md`, `behaviours/compaction.md`:

1. **Offsets with gaps.** After compaction "offsets never move; batches keep base offset and offset span, so records leave gaps" and "a stored batch spans its offsets, whatever records compaction left in it" (`phase7.md`, commit `ac795b7`). The log walks advance by last-offset-delta, not record count (CMP-6). A console can draw which offsets in a partition are gone, and which ones the cleaner kept only as empty batches (to keep the last offset or a producer's last sequence).
2. **Segments as an object.** Real Kafka's admin protocol shows a log directory total (DescribeLogDirs) at best. Here each segment has a base offset, next offset, size, modified time, newest timestamp, two files and an index, an active one and sealed ones (typestate `ActiveSegment` / `SealedSegment`); `segment.bytes` and `index.interval.bytes` act at runtime on the next roll (ADM-6). `segment.ms` rolls an idle active segment.
3. **Compaction as a visible state machine.** Planner inputs and outputs are pure and cheap (`judge`): checkpoint, first dirty offset, dirty vs clean bytes, `upto` (limited by the active segment, the first open transaction, or a segment newer than `min.compaction.lag.ms`), the lag escape hatch `max.compaction.lag.ms`. A user can be told why a compacted topic has not compacted. Atomicity is visible on disk: `.cleaned` / `.tmp` replacement files, `.swap` and renames "safe against a stop at any point" (`compact.rs`, `log/compact.rs`), per-partition `cleaner-checkpoint`.
4. **Compaction and transactions interplay.** "Aborted data goes; a marker stays while a record of its transaction does; only below the last stable offset" (`phase7.md`); `compact/txn.rs` `AbortedTxn`; `compact/types.rs` `LastOf{data_last_offset, marker_epoch}` per producer (what the cleaner must not lose).
5. **Tombstone aging** (`delete.retention.ms`, `compact/retain.rs`): a tombstone has an age and a removal date.
6. **Config semantics:** `compact,delete` compacts first then retains after; keyless record on a compacted topic is refused INVALID_RECORD with per-record errors (`handlers/produce/check.rs` `require_keys`).
7. **Start of log moves**: `DeleteRecords` and retention move `log-start` (file), which `Fetch` and `ListOffsets` honour; `OffsetOutOfRange`/"log start moved" states exist as Go boards (Tp-30) and have data here.
8. **Resource cost per partition** (descriptors, open/closed LRU) and the clean-shutdown/vouch marker are doze-specific facts.
9. **Single-writer log with tickets:** an append's durability is a `Ticket` resolved by one group fsync (PLAN design). "Acked but not yet durable" vs durable is observable per partition in principle (`append_seq` vs `synced_seq`, `log.rs`).

## PART 3. What the doze-aws console direction established

Artifact: https://claude.ai/artifact/JkCiMcWtKs5doXpxUQghuS (slug 8fb38ec7-...). Pages read: Main (Brief), Vanity, Scope, Spaces, Patterns, System, LiveB, LiveBLoad. Treated as data. Nothing in it was verified against real AWS (its own footers say so).

### 3.1 Thesis (Brief)
"If AWS built this for the people who build on it." Today's console is an admin tool (one page per service). The direction treats the console as a product with **jobs** for a developer, using what only doze can see: every call the app makes, on their own machine, instantly. Shifts: organised by what you are doing (six labelled spaces) not by service; shows what the app is doing as it happens; guided doing with the real API call beside it; the wire and the map are one space, kept 3 hours; a refusal is explained (which rule, what would pass); both addresses with snippets.

### 3.2 The five jobs
01 **Connect** (point my app at this; know it worked when the first call lands; lives in Home). 02 **Watch** (what my app is doing now; Live). 03 **Build** (create, send, peek, invoke with AWS words; Resources). 04 **Understand** (why refused/denied/slow, smallest permission; Access). 05 **Rehearse** (break it on purpose, rewind; Lab, later). "Every screen exists to serve one of these. If it serves none, it does not ship."

### 3.3 Principles (Brief)
Familiar words, better flow (keep AWS names, not page-per-service). Live by default, forgetful by design (hours not days, fixed-size memory ring, costs nothing while closed). Every screen answers four things: where am I, what is the state in words, what can I do, what just happened. Motion means an event. Teach at the point of doing. Refuse like AWS and say why. **Not goals:** pixel copy, a monitoring product, features without data behind them, phones (<768 px unsupported).

### 3.4 Real or vanity (Vanity)
Four tests: answers a question asked while building; data held already or holdable for hours at almost no cost; useful in ten seconds without reading; still wanted on day ten. Fails two = deferred or cut. **Weight rule:** the console costs nothing while closed; live feed is a server-sent stream opened only when a space that needs it is on screen; history is a fixed-size in-memory ring; **no polling, no database**. Verdicts: Build (connect page, wire as a space, copy-as CLI/curl, live map, one number per resource, explain a refusal), Build small with a stated limit (replay with side-effect confirm, caller by access key, 3 h per-minute counts, least-privilege policy from calls), Later (fault rules, checkpoints, parity badge, export to CloudFormation), **Cut** (cost estimate, replay a whole session, ambient motion/glow/particles, "insights"/AI summaries, a dashboard per service). Minute buckets: 3 h of small integers per resource and per app. "Restart clears history. The console says 'since 14:02'."

### 3.5 Six spaces (Spaces)
Rail of at most seven labelled items: Home (Connect), Live (Watch), Resources (Build), Access (Understand), Lab (Rehearse, later), Settings. Pinned and Recent are resources, not services. Resources groups services into six domains (colour belongs to a domain never a service). Address shape keeps service words: `/resources/sqs/queues/pick-lists`, `/live?app=payments`. "A resource has exactly one home address; everything else links to it." ⌘K reaches everything. **A service never gets chrome of its own.** Removed: 17 icons, a landing page per service, the wire as a footer panel, settings per service.

### 3.6 Six page patterns (Patterns)
Four questions in four places on every page (path; live sentence; verbs; "what just happened" dock). Patterns: **1 Space home** (title, one sentence, "needs you" strip, <= 3 cards); **2 Browse** (list left, selection right, filter as you type, j/k, one live number per row, New top right); **3 Resource** (path, name + live sentence + verbs, connections strip, tabs, wire dock; in this order); **4 Create** (form left, the real API call right, teaching lines under each field, limits from the API model, "what this will be wired to"); **5 Peek drawer** (live sentence, short history strip, verbs, Open; Esc closes); **6 Empty** (one sentence, one primary action, "or from your app" snippet with both addresses).

### 3.7 System (layers, tokens, descriptor)
Five layers pointing down: Foundations (tokens as roles, type, 4 px grid, radius, motion, density) -> Primitives -> Components (resource header, wire row, wire dock, map node, connection strip, result word, teaching field, payload view, endpoint chip, sparkline, palette, drawer, toast) -> Patterns -> Spaces. Rule: a component uses only primitives and tokens, a pattern only components, a service only patterns through its descriptor.
Tokens are roles, values from the doze brand (`doze/internal/desk/frontend/src/tokens.css`, generated by `internal/brand`), shown dark violet / light violet: bg `#15131d`/`#fbfaff`, side `#110f18`/`#f3f1fa`, panel `#1b1927`/`#ffffff`, line `#2c2840`/`#e4e0f0`, text/dim/bright `#cfcbe3 #8a85a8 #f4f1ff` / `#3a3550 #6f6888 #17141f`, accent `#bd93f9`/`#7a4fe0`, good `#7ee787`/`#17773f`, warn `#f2c879`/`#9a6400`, bad `#ff7a93`/`#cc3550`, cool `#82aaff`/`#2f62d9`; two **new** roles: `refused` (distinct from accent and bad; Scope board uses orchid `#a3279a`) and six **domain** hues (thin bar or glyph tile, never text, never status; Scope/Spaces boards use teal `#0f8a8f`, blue `#2f62d9`, orange `#c2610a`, brown `#8a5a2b`, green `#5b7f2a`, grey `#6f6888` as placeholders). Type: Inter for text, JetBrains Mono for names/numbers/times, sizes 11 12 13 14 16 20 22, sentence case, tabular figures. 4 px grid, radius 7/10/12, list rows 48 px, rail 224 px (the boards draw 184), flat cards, shadow only on floating things. Motion: hover/toggle 120 ms, panels/drawers 200 ms, a bead crosses an edge in about 2 s, once, per real call. ### 3.8 Scope rules (Scope)
"When doze can't do it, it says so in three places": (1) in a form before creation (an option that cannot work stays visible, greyed, with its reason, "Not available in doze-aws: it would need a mail server"); (2) on the resource afterwards (a "Not active locally" grey badge on things scripts created that are accepted and stored but do nothing; a banner with a count); (3) on the wire (a `NOT BUILT` word and HTTP 501 with an `X-Doze-Not-Built` header and "what works instead"). Tiers: F functional, C cosmetic (stored only), S declined (501). Surfaces in a "Needs a look" strip on Live. Rules: never silent; words then colour (four states, four words: Refused, Would be denied, Not active locally, NOT BUILT); truth from one place (the same support table the engine uses); the status is part of the service descriptor (typed data).

### 3.9 Live map rules (LiveB, LiveBLoad)
Direction **B (Paper, light, transit-line map)** chosen 2026-11-08. ### 3.10 Motion, refusal/denial language, teaching
- Motion: "Something moves only because a real call happened. Nothing animates at rest. Reduced motion gets the same information as a highlighted row." One bead per wire row, about 2 s, click highlights the route.
- Refusal vs denial: **REFUSED** (AWS itself would refuse; orchid, slashed-circle glyph, "400 InvalidParameterValue") vs **WOULD BE DENIED (soft)** (your identity lacks permission; amber triangle) vs **NOT BUILT** (slate); never colour alone; always carries words; the explain panel says which rule fired and what would pass. "The console never offers what the API would refuse."
- Teaching under the field: five lines: name and unit; value in plain words; what it does; range and default; the neighbour check from real data. Limits come from the API model, not from memory.

### 3.11 Owner's rules from memory notes
- `doze-aws-console-rethink.md`: owner's complaint was "basic and utilitarian, no wow or oomph"; wants doze app/website standard; **design comes before any Rust console code**; six spaces not N icons ("not 'add another similar looking left menu icon'"); real-time with hours of history, "has to feel cool", flag vanity vs real; show both .doze URLs and IP:port when run by doze, standalone/Windows shows IP only; Refused vs Denied distinct; **publish pages to the canvas as they are ready**; doze brand tokens; owner asked for realism on build difficulty, a busy account (too many resources), per-row actions varying by call; rules agreed: map shows flows not every resource; wire rows aggregate repeats; history buckets updated on the request path (no timer, zero idle wake-ups); actions computed per row; a not-built feature is a disabled option with a reason, stored-only is a badge, 501 is a wire word.

### 3.12 What carries over, what does not (factual mapping, no design)

Carries over as a method or rule:
- Jobs-first thesis; the "serves none of the jobs, does not ship" test; the four-question page; real-or-vanity four tests and the cut list; grounding rule with Exists/New tags; refused/denied/not-built words with colour never alone; scope-in-three-places; "motion is an event"; teaching lines drawn from the model (Kafka has them: `topic_config/docs.rs` and `internal/settings`); descriptor-driven pages (Rust console crate rendering typed view-models: the PLAN already says so); five-layer system and brand tokens (shared with the doze app and website); publish-as-ready; render-and-look; board-by-board comparison.
- The Go Kafka console already uses the same instinct in places (one vocabulary for "no", confirms that tell the truth, teaching lines from `internal/settings`, "what will be sent" preview, honest budget statements in the trace scan), so a Kafka direction extends rather than starts it.

Does not carry over unchanged (facts that differ):
- **No `.doze` names for Kafka.** `PLAN.md`: "IP and port only. doze-kafka no longer uses doze-names." The "both addresses" Home/Connect rule has no second address; what remains is bootstrap vs the *advertised* listener rule (a client reconnects to the advertised address, `connect.html` "Two things that catch people").
- **Caller identity.** AWS: access key per app. Kafka: client.id (self-declared, often empty or default), software name/version from ApiVersions, remote address, principal only once SASL exists (Phase 8). No "key per app" mechanism is described for Kafka.
- **IAM soft mode / "would be denied".** No soft mode exists for ACLs in either edition that I found; denied is real (Phase 8).
- **Polling vs streaming.** The AWS direction says "no polling... a server-sent stream opened only while the space is on screen". The Rust plan for the Kafka console says htmx `every 3s` polling (`PLAN.md` design table). These conflict and need an owner decision; the Go console polls at 2.5 to 5 s.
- **Request bodies.** AWS direction needs new capped capture for copy-as/replay. The Go Kafka recorder deliberately never records bytes or header values; Kafka requests are binary and the useful replays are "produce this record again" (resend exists) and "fetch from here" (offset links), not raw request replay.
- **Fault rules need a gateway hook.** Kafka's equivalent hook is `Broker::handle` / `exchange()`, but production builds carry no fault seam by design (Go: build-tagged `internal/faultinject`, verified absent from a normal binary by `build_test.go`; Rust: `SimFs` behind feature `sim`, "No globals, no feature-flagged code paths in production").
- **Space count.** The AWS six spaces were sized for 17 services and ~450 screens. Kafka has few resource kinds (topic, partition, group, producer/transaction, ACL/principal later, schema subject later). Whether six spaces fit is a design question (flag only).
- **The Go design and e2e contract already exist** (about 100 boards, a 34-spec DOM suite and an element-level design gate). Phase 9 of the Rust plan says the suite passes unchanged. A new direction either keeps that DOM (pure re-skin through the existing gate) or the owner must retire/replace the contract. That decision is not made anywhere I read.

Cross-cutting dependencies that gate many jobs at once (facts, not design):
1. A read-only inspect surface on `Broker`/`LogReader` (Part 2 central fact). Gates K3, K4, K5, K7, K8, K9, K10, K15, K16.
2. A request observer in `kafka-server/src/connection.rs:exchange` and a bounded in-memory recorder. Gates K1 (first-call check), K2, K6 (partly), K14, and writer attribution in K5/K7. The Go recorder is the spec for bounds and clipping; the Rust design has no reflection, so a `Summarize` per API is new code (about 41 served APIs, `SERVED` in `broker.rs`).
3. A small cause/event vocabulary at the points that already make decisions: `begin_rebalance`, `Producers::check`, `Refused`, `Cleaned`, `Trim`. Gates K3, K6, K8.
4. Polling vs server-sent stream decision (Part 3.12) and the "no flat DOM contract" decision about the 34-spec suite.
5. Weight: any recorded state is bounded and lazily built; Go's TRF-1 (a 900 KiB join reason once cost 1.8 GiB) is the warning for clipping client-chosen strings; Rust idle RSS is 4.4 MB and "may only rise with a written reason" (`docs/port/weight.md`).
