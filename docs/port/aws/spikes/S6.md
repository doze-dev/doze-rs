# S6: redb with a group-commit flusher on SQS-shaped load

Status: **predictions written 2026-11-09, before any measurement.** Results are appended below the line when measured.
Code and raw numbers: scratchpad `spike-s6-store` (not in the repo).

## Hypothesis (from `phase0.md`)

redb (the version kafka pins, `=4.5.0`) on the `Fs` seam with a group-commit flusher meets SQS-shaped load: one redb table of
messages, send / receive / delete of 1 KiB messages, with a per-op latency that a developer would not notice at 1k and 10k messages
per second, durability on and off. Fallback: an append log for hot queues.

## Finding before measuring

`crates/kafka-meta` has **no group-commit flusher**. Its writes are one at a time under a mutex, each `Durability::Immediate`.
`PLAN.md` puts one in `doze-store`; it has to be written, not extracted. The spike writes the smallest correct one: a dedicated
thread owns the `Database`; callers send an operation and a reply channel; the thread takes whatever is queued, applies it in one
write transaction, commits once, then acknowledges every caller (or fails every caller if the commit failed). No transaction is held
across an `.await`.

## Method

Workload per message: send (insert into `messages` keyed by queue id and sequence), receive (set a visibility deadline and bump the
receive count), delete (remove). That is three write operations per message. Open-loop offered load of 1,000 and 10,000 messages per
second for 15 s each, one hot queue plus 99 idle ones; latency is the time from offering a send to its acknowledgement
(coordinated-omission-safe: timestamps are the scheduled times). Reported: p50 and p99 of send, achieved rate, commits per second
(= syncs per second, counted in the backend), mean batch size. Variants: durable (`Immediate`) and not durable (`Durability::None`,
flushed once a second); ungrouped (one commit per operation, kafka-meta's pattern); an append-log alternative (one file, records
`[kind, queue, seq, len, payload]`, in-memory index, group commit, no compaction). Lazy open/close: 200 cycles of open an existing
database, one read, close (explicit `close()`), then the same with a plain drop; time and syncs per cycle. Hosts: this Mac and the
Lima VM `doze-ubuntu`.

## Predictions (made 2026-11-09)

| Quantity | Prediction |
|---|---|
| One durable commit | macOS 2.5 to 4 ms (`sync_data` is `F_FULLFSYNC` there); Linux VM 1 to 3 ms |
| Ungrouped, durable, macOS | caps near 250 to 400 ops/s, so it **cannot** keep up with 1k messages/s (3k ops/s): latency grows without bound |
| Grouped, durable, 1k msg/s | send p50 3 to 6 ms, p99 under 12 ms; 250 to 330 commits/s; mean batch about 10 operations |
| Grouped, durable, 10k msg/s | send p50 4 to 8 ms, p99 under 20 ms; 250 to 330 commits/s; mean batch about 100; keeps up (no growing backlog) |
| Grouped, not durable, 10k msg/s | send p50 under 0.3 ms, p99 under 3 ms; about 1 sync per second |
| Append log, durable, 10k msg/s | p50 and p99 within 20 percent of redb grouped (both bounded by the sync); lower CPU |
| redb CPU at 30k ops/s | 20 to 40 percent of one core |
| Open an existing database | under 2 ms, 0 syncs |
| Explicit close | 8 to 15 ms on macOS, 2 to 3 syncs (matches `weight.md`); 3 to 8 ms on Linux |
| Drop without close, then reopen | no repair needed (redb closes on drop), so the same as an explicit close |

## Predicted verdict

The hypothesis holds: with grouping, a single flusher thread meets both loads, durable or not. Without grouping it fails by an order
of magnitude. The append log is not needed for latency; its case would be CPU and file growth under sustained 10k msg/s, which the
spike will show as a number. Lazy open is cheap; lazy close costs a sync or two and belongs off the request path (reap in the
background, as the plan says).
