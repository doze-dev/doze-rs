# S6: redb with a group-commit flusher on SQS-shaped load

Status: **measured 2026-11-09.** The predictions were written first and are unchanged; the results follow the line.
Code and raw numbers: scratchpad `spike-s6-store` (not in the repo).

## Hypothesis (from `phase0.md`)

redb (the version kafka pins, `=4.5.0`) on the `Fs` seam with a group-commit flusher meets SQS-shaped load: one redb table of
messages, send / receive / delete of 1 KiB messages, with a per-op latency that a developer would not notice at 1k and 10k messages
per second, durability on and off. Fallback: an append log for hot queues.

## Finding before measuring

`crates/kafka-meta` has **no group-commit flusher**. Its writes are one at a time under a mutex, each `Durability::Immediate`.
`PLAN.md` puts one in `doze-store`; it has to be written, not extracted. The spike writes the smallest correct one: a dedicated
thread owns the `Database`; callers send an operation and a reply channel; the thread takes whatever is queued, applies it in one
write transaction, commits once, then acknowledges every caller (or fails every caller if the commit failed). No transaction is held
across an `.await`.

## Method

Workload per message: send (insert into `messages` keyed by queue id and sequence), receive (set a visibility deadline and bump the
receive count), delete (remove). That is three write operations per message. Open-loop offered load of 1,000 and 10,000 messages per
second for 15 s each, one hot queue plus 99 idle ones; latency is the time from offering a send to its acknowledgement
(coordinated-omission-safe: timestamps are the scheduled times). Reported: p50 and p99 of send, achieved rate, commits per second
(= syncs per second, counted in the backend), mean batch size. Variants: durable (`Immediate`) and not durable (`Durability::None`,
flushed once a second); ungrouped (one commit per operation, kafka-meta's pattern); an append-log alternative (one file, records
`[kind, queue, seq, len, payload]`, in-memory index, group commit, no compaction). Lazy open/close: 200 cycles of open an existing
database, one read, close (explicit `close()`), then the same with a plain drop; time and syncs per cycle. Hosts: this Mac and the
Lima VM `doze-ubuntu`.

## Predictions (made 2026-11-09)

| Quantity | Prediction |
|---|---|
| One durable commit | macOS 2.5 to 4 ms (`sync_data` is `F_FULLFSYNC` there); Linux VM 1 to 3 ms |
| Ungrouped, durable, macOS | caps near 250 to 400 ops/s, so it **cannot** keep up with 1k messages/s (3k ops/s): latency grows without bound |
| Grouped, durable, 1k msg/s | send p50 3 to 6 ms, p99 under 12 ms; 250 to 330 commits/s; mean batch about 10 operations |
| Grouped, durable, 10k msg/s | send p50 4 to 8 ms, p99 under 20 ms; 250 to 330 commits/s; mean batch about 100; keeps up (no growing backlog) |
| Grouped, not durable, 10k msg/s | send p50 under 0.3 ms, p99 under 3 ms; about 1 sync per second |
| Append log, durable, 10k msg/s | p50 and p99 within 20 percent of redb grouped (both bounded by the sync); lower CPU |
| redb CPU at 30k ops/s | 20 to 40 percent of one core |
| Open an existing database | under 2 ms, 0 syncs |
| Explicit close | 8 to 15 ms on macOS, 2 to 3 syncs (matches `weight.md`); 3 to 8 ms on Linux |
| Drop without close, then reopen | no repair needed (redb closes on drop), so the same as an explicit close |

## Predicted verdict

The hypothesis holds: with grouping, a single flusher thread meets both loads, durable or not. Without grouping it fails by an order
of magnitude. The append log is not needed for latency; its case would be CPU and file growth under sustained 10k msg/s, which the
spike will show as a number. Lazy open is cheap; lazy close costs a sync or two and belongs off the request path (reap in the
background, as the plan says).

## Results (measured 2026-11-09)

What was built (scratchpad `spike-s6-store`): redb `=4.5.0` on a copy of kafka's `Fs` seam and `FileBackend` (a counting wrapper around `sync_data`);
one table `messages: (queue u32, seq u64) -> 12-byte header + 1,024-byte body`; **the group-commit flusher written for this spike** (about 40 lines): one
thread owns the `Database`, takes everything queued (up to a cap), applies it in a single write transaction, commits once, then answers every caller;
nothing is held across an `.await`. Callers wait on a oneshot. Not durable means `Durability::None` with one `Immediate` batch a second. The spike code
unwraps; a real flusher must fail every waiting caller on a failed commit and refuse everything after. The append-log alternative is one file,
records of 13 to 1,053 bytes, an in-memory index, the same group commit, **no compaction and no recovery**. 100 queues, 99 idle with 100 messages each (about 16 MiB).
Open-loop load of the hot queue: 15 s per cell (5 s for the ungrouped cells, 10 s drain allowed). "From schedule" is measured from the instant the
send was due (no coordinated omission) and includes up to a millisecond of timer lag of the load generator itself; "from issue" is measured from the call.
Receive and delete are measured from issue. One run per cell.

**`kafka-meta` has no group-commit flusher**, so `doze-store` has to write one (the spike's is a starting point, not production code). Its writes are
single, immediate-durability transactions under a mutex.

### Verdicts

1. **The hypothesis holds on the hard case (a 3 ms fsync).** With a group-commit flusher, redb serves 1k and 10k messages a second (3k and 30k write operations a second)
   at a median of about 6.4 ms and a p99 of 9 to 13 ms durable, and about 0.04 ms (p99 0.1 ms) not durable, on one flusher thread using 5 to 14% of a core.
   Throughput is bounded by the sync (about 240 commits a second here), so the batch size grows with the load (12 at 1k, 125 at 10k). The median is
   about two syncs, not one: a request waits for the commit in progress and then for its own.
2. **Without grouping it fails by more than ten times** when the sync is expensive (243 ops a second against 3,000 needed). Not durable, grouping is
   not needed (29,876 commits a second, p50 0.09 ms), so the flusher is about durability only. Where a sync is nearly free (the VM) an ungrouped writer keeps
   up at 1k msgs/s, so the case for grouping depends on the disk; the Mac is the realistic floor for a developer laptop.
3. **The append log is not needed for latency.** It is a little faster (p99 about 35% lower) and uses a fifth of the CPU, but it grows 1.05 KiB per
   message with no compaction (154 MiB for 150,000 messages against redb's flat 16 MiB) and needs its own recovery. Keep it as the fallback only for a queue whose
   measured CPU matters.
4. **Lazy open and close:** open costs one sync (3.3 ms on the Mac), a clean close four syncs (about 11 ms), a dirty reopen five syncs and 21 ms. All off the request
   path if the reaper closes in the background; a first request after a reap pays about 3 ms. Dropping a database is as good as closing it.
5. **For `doze-store`:** cap the batch (largest seen was 408 operations on macOS, 715 on the VM; a cap of about 1,024 bounds the commit time); acknowledge only after the commit;
   fail all waiters on a failed commit; do durable-by-default with a documented opt-down to the one-sync-a-second mode, which costs about 150 times less latency.

### Caveats

One run per cell. Loopback-free (no network), but the load generator shares the machine and its timer lags up to a millisecond (hence "from issue"). Nothing was
tested for crash safety of the flusher (SimFs was not used); the durability claim here is only that the sync happens before the acknowledgement. One hot queue of 1 KiB messages;
no FIFO groups, no long polling, no big batches, no 256 KiB bodies. The VM numbers need a real Linux disk before anyone quotes them.
