# S1: do the types and schema tables for all 18 service models fit in 3 MiB at fat LTO?

Status: **prediction written 2026-11-09, before any measurement.** Result and verdict are appended below the line when done.
Code and raw numbers stay in the scratchpad (`spike-s1-codegen-full`), built on spike A (`spike-a-codegen`, 2026-11-08).

## Hypothesis (from `phase0.md`)

Types and schema tables for all 18 models fit in 3 MiB stripped at fat LTO, with the table-driven decoder exercised on every
operation. Fallback if false: a cargo feature per service, and `opt-level = "z"` on the model crates.

## What is already known (spike A, thin LTO, opt-level 3, 1,372 operations, about 6,200 shapes)

- Tables only (every operation's metadata, errors, routes and wire schema walked): 1.48 MiB.
- Serde-derived decode and encode on every type: 13.2 MiB, so about 1.9 KB per shape. That path is rejected.
- Nobody has measured the plan's actual design yet: typed structs, schema tables, and **hand-written** decode and encode driven by the tables.

## What this spike builds and measures

Design under test: generated plain structs, enums and constraint newtypes (no serde); generated schema tables; generic wire codecs
(JSON, Query, REST, XML) producing a value tree; and a thin generated glue per type that builds the typed value from the tree using
hand-written helpers, plus the reverse for responses. A generated dispatch (`decode_input(op, tree)`, `encode_output(op, value)`)
keeps every operation's code alive, as a real server must.

Variants, each at fat LTO, `codegen-units = 1`, `panic = abort`, strip, at opt-level 3 and opt-level z:

| id | what is called | answers |
|---|---|---|
| T | tables and generic codecs only | the floor |
| I | T + typed decode of every operation's input | decode cost |
| IO | I + typed decode of every output | accounting step |
| IOE | IO + encode of every output | with IO, isolates the encode cost |

Server-realistic size = I + (IOE - IO). Per-service sizes come from one binary per service.

## Predictions

| quantity | prediction |
|---|---|
| T, all 18, opt 3 | 1.4 MiB (spike A's 1.48 MiB at thin LTO, minus a little for fat LTO) |
| T, all 18, opt z | 1.1 MiB |
| I, all 18, opt 3 | 3.0 MiB |
| server-realistic (I + encode), all 18, opt 3 | **4.2 MiB** |
| server-realistic, all 18, opt z | **3.3 MiB** |
| fat vs thin LTO | fat saves 5 to 10 percent |
| largest single service | SSM, about 0.7 MiB server-realistic at opt 3 |
| any five services (SQS, SNS, SSM, Secrets Manager, KMS) | under 1.5 MiB at opt 3 |
| eager vs lazy RSS | eagerly touching every table page adds up to about 1.5 MiB RSS; compiling every constraint regex eagerly adds 3 MiB or more of heap; lazy adds close to nothing |
| full fat-LTO build of the use-everything binary | under 4 minutes wall on this Mac |
| constructs the generator cannot express | the 52 look-around patterns, documentation-only constraints, and the SQS, SNS and similar limits that the models do not state at all |

Predicted verdict: **PASS with feature-gating.** The all-18 build exceeds 3 MiB on the server-realistic path; the typed-glue cost is
the unknown, and the plan's "decode tables included" ceiling of 3 MiB probably assumed it was close to free.

# Result (2026-11-09)

Machine: Apple silicon Mac, rustc 1.99.1, `lto = "fat"`, `codegen-units = 1`, `panic = abort`, strip. Sizes are stripped files in MiB.
An empty Rust binary is 0.29 MiB (opt 3) and 0.27 MiB (opt z). All 18 models, 1,372 operations, about 6,200 shapes, 16,595 schema members.
Generated: 145k lines of types, 54k of schema tables, 169k of glue. Code and raw numbers: scratchpad `spike-s1-codegen-full` (`results/matrix.jsonl`).

What was built: the spike A generator with a new `--glue` mode (per-type `Decode`/`Encode` impls, no serde derive) over a hand-written
runtime (`smithy-rt/src/glue.rs`, a `serde_json::Value` tree and about 300 lines of helpers), plus a generated per-service dispatch
(`decode_request`, `decode_response`, `encode_response`, an `AnyError` enum). The probe calls every operation's dispatch with a tree
shaped from the operation's own schema. The trees are schema-shaped, not valid requests (strings are `"a"`), so many decodes end in a
constraint error; every code path is still linked and reachable, which is what the size needs.

## All 18 services, one binary

| variant | opt 3 | opt z | predicted (opt 3) |
|---|---|---|---|
| T: tables and generic codecs | 2.25 | 2.21 | 1.4 |
| I: T + typed decode of all inputs | 5.42 | 3.73 | 3.0 |
| IO: I + typed decode of outputs and errors | 8.06 | 4.93 | n/a |
| IOE: IO + encode of outputs and errors | 9.25 | 5.41 | n/a |
| **server-realistic: I + (IOE - IO)** | **6.61** | **4.21** | 4.2 |

These are the best glue (v3). The first glue gave 7.06 / 4.27. Two experiments that did not help: removing probe duplication changed
nothing (identical bytes); forcing the helpers inline made it worse (I = 7.12). Moving the map lookup and path handling out of line
saved 7 percent (I 5.83 to 5.42). The output decode (IO - I) exists only to give the encode a value; it is not part of a server.

## Where the bytes are (cargo-bloat, I, unstripped)

Text is 3.75 MiB of the file. Per-instance helpers `Cx::req/opt::<T>`: 1.19 MiB over 1,276 instances (v1; about 0.8 after the fix). Struct/union/newtype
`Decode::decode`: 0.70 MiB over 578 functions. Dispatch: 0.18 MiB. The rest is rodata (the tables, member-name strings duplicated into the glue) and std.
**The floor T alone is 2.2 MiB, so tables plus generic codecs use three quarters of a 3 MiB ceiling before any typed code exists.**
Typed glue costs about 0.5 KB per shape for decode alone and about 1 KB per shape with encode.

## Per service (v1 glue, opt 3, server-realistic, standalone binary; each includes the 0.29 base and about 0.4 of shared codec)

sqs 0.57 | sts 0.57 | sns 0.59 | secrets-manager 0.61 | sfn 0.65 | kinesis 0.70 | kms 0.72 | apigatewayv2 0.78 | cloudwatch 0.80 | api-gateway 0.81 | eventbridge 0.84 |
iam 0.93 | cloudformation 0.97 | dynamodb 0.99 | lambda 1.02 | logs 1.07 | s3 1.15 | ssm 1.56. Sum 15.8 (it overcounts the shared part).
Marginal cost of a service in a combined binary is its standalone size minus about 0.5. SQS+SNS+SSM+Secrets+KMS together: 1.93 (opt 3) and 1.37 (opt z).
Derived, not built: at opt 3 the eleven cheapest services (through EventBridge) total about 2.6 MiB and IAM tips it over 3; at opt z (about 0.64 of opt 3)
fifteen services fit and SSM, S3 and Lambda do not.

## Compile time

Clean build of the use-everything binary (all 18 crates and the fat-LTO link): **5 min 42 s** at opt 3 (412 s CPU), **44 s** at opt z (89 s CPU).
The link alone, with crates already built: 1.5 to 6 min at opt 3 (I to IOE), 17 to 33 s at opt z. Predicted under 4 minutes: missed at opt 3.

## Idle RSS: lazy versus eager (the all-18 IOE binary, macOS `max resident set size`, median of nine)

| mode | MiB |
|---|---|
| empty binary | 1.89 |
| all 18 linked, nothing touched | 3.59 |
| every operation's schema table walked | 4.44 (+0.85) |
| every one of the 447 constraint regexes compiled | 26.75 (+23.2, about 52 KB each) |

Tables are read-only data and cost only the pages touched, so eager tables are cheap. Regexes must stay lazy (the existing `OnceLock` pattern does this). A first
request that hits a pattern shape costs about 50 KB of heap; the Unicode-class patterns are the heavy ones.

## What the generator cannot express

- **52 patterns `regex-lite` cannot compile** (listed in the generator output `results-gen.txt`): 22 use look-around (14 of them are the same `^(?!\s*$).+$`, "not blank"; the others are look-behind, look-ahead and a back-reference), 27 use Unicode properties (`\p{L}`, `\p{Z}`, `\p{N}`, `\p{P}`, `\p{M}`, `\p{Print}`: tag keys and values, descriptions), and 3 are others (`[\w-_]`, a class with UTF-16 surrogate escapes, and an IAM role ARN pattern with `{1,1017}`; the rejection cause of these three was not checked). All need hand predicates keyed by shape id.
- **Documentation-only traits** are ignored and cost nothing on the wire: `documentation` (17,360 uses), `tags` (2,076), `examples` (274), `paginated` (208), `waitable` (22), `smokeTests` (20), endpoint rule sets and BDDs (54), `iamAction` (88; needed later for IAM action tables, not by the codecs), `conditionKeys` (29).
- **Not stated by the models at all:** SQS has no length, range or pattern traits; many services state limits only in prose; cross-member rules (FIFO name suffix versus the FifoQueue attribute, mutually exclusive parameters, conditional required members), quotas that count resources, which validation error code a service uses (ValidationException, InvalidParameterValue, InvalidParameter), and the `strict-fields` behaviour (the glue is lenient about unknown members).

Overlay mechanism needs (today: `shapes` replacement and `retarget`, as in `overlays/sqs.json`): add a per-service predicate registry for uncompilable patterns;
cross-field rules as data (member A requires/forbids B; name suffix tied to an attribute); the validation error-code mapping per service; quota limits as a table checked
by the service, not the codec; and an evidence tag (`docs` or `recorded`) on every overlay entry, so the limit prober's output can replace prose.

## Verdict: FAIL as specified; the fallback also fails for all 18 in one binary

- All 18, typed, one binary: **6.61 MiB (opt 3) and 4.21 MiB (opt z)** against 3.0. Both miss. The prediction's all-18 figure (4.2) was right only for opt z by accident; its premise (T = 1.4) was wrong by 0.8 MiB.
- Fallback measured: cargo feature per service and opt z. It fits about eleven services at opt 3 and about fifteen at opt z, never all 18.
- For scale, the Go binary is 30 MiB (31,588,738 bytes built from origin/main), so even 6.6 MiB is a fifth of it. The 3 MiB ceiling was our own number, and the typed-struct design cannot meet it.

## Recommendation (for the owner to decide; not applied)

1. Do not generate typed decode and encode for every operation. SCOPE.md already makes most operations accept-and-store (tier C) or refused (tier S). Generate typed glue only for tier-F operations (the ones with behaviour) and let the rest ride the generic stored-document path, which needs only tables. Measure this as spike S1b: restrict `--glue` to the operations SUPPORT.md marks F. Expectation, unmeasured: T (2.2) plus a third to a half of the typed cost, so 3.5 to 4.5 MiB at opt 3.
2. If a hard 3 MiB matters, the only design measured to fit is T-shaped: tables and generic codecs plus a schema-driven validator on a dynamic tree, with no per-type code. T is 2.2 MiB and the validator is unmeasured (constraints are not in the tables yet). Cost: handlers read members through accessors, not typed fields.
3. Re-state the budget as a pair: "all services, typed where it matters: at most 5 MiB at opt z" and "five services: at most 1.5 MiB", and gate the first in CI.
4. Keep regexes lazy and build constraint tables per service on first use (already the weight rule).
5. Windows and x86 sizes are not measured (macOS arm64 only).
