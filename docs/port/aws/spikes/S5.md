# S5: allocator and RSS after load

Status: **measured 2026-11-09.** The predictions were written first and are unchanged; the results follow the line.
Code and raw numbers: scratchpad `spike-s5-alloc` (not in the repo).

## Hypothesis (from `phase0.md`)

With the system allocator, RSS returns near baseline after (a) a 1 GiB streamed upload through a hyper server into a file and
(b) a burst of 10k concurrent small request/response cycles with about 64 KiB bodies. If not, the frame-pool pattern
(`crates/kafka-server/src/pool.rs`) suffices. Fallback if neither: a `doze-alloc` crate holding one `unsafe` call (`malloc_trim`
on glibc), mimalloc on macOS.

## Method

One server binary (hyper 1.x, tokio current-thread, as the plan says) and a separate load binary, so the server's RSS is its own.
Server handler: (a) streams the request body frame by frame into a file; (b) collects the whole body, holds it 300 ms (a request in
flight), answers with 64 KiB. Allocators, chosen at build: system; system plus one `malloc_trim(0)` after the load (Linux only);
mimalloc; jemalloc (tikv-jemallocator). A variant with the kafka-style frame pool for the request bodies. RSS is read from `ps`
(macOS, plus `footprint` where it works) and `/proc/PID/status` (Linux). Sampled before the load, at the peak, 10 s after the load
ends, and also 30 s after (jemalloc decays on a 10 s timer). Hosts: this Mac (Apple M5 Max, macOS 27, arm64) and the Lima VM
`doze-ubuntu` (Ubuntu 24.04 arm64, glibc, 4 CPUs, 4 GiB). A fresh server process per run.

## Predictions (made 2026-11-09)

Baseline = the idle server before any load.

| Quantity | Prediction |
|---|---|
| Baseline RSS | macOS 4 to 7 MiB; Linux 2 to 5 MiB, any allocator (mimalloc and jemalloc +1 to 3 MiB) |
| (a) 1 GiB upload, peak over baseline | at most 12 MiB, every allocator, both hosts |
| (a) 10 s after | within 5 MiB of baseline, every allocator |
| (b) burst, peak RSS | 700 to 1000 MiB (640 MiB of bodies plus per-connection buffers) |
| (b) 10 s after, system allocator, macOS | **retains at least 300 MiB: the hypothesis fails here** (this is what the kafka frame pool was made for) |
| (b) 10 s after, system allocator, Linux glibc | retains 100 to 400 MiB (fragmentation: 64 KiB blocks sit under the 128 KiB mmap threshold) |
| (b) glibc plus one `malloc_trim(0)` | back under 50 MiB over baseline |
| (b) mimalloc | back under 40 MiB over baseline within 10 s, both hosts |
| (b) jemalloc | under 60 MiB over baseline at 10 s on Linux; more on macOS; under 40 MiB at 30 s |
| (b) frame pool alone (64 MiB shelf bound, 64 KiB class) | **does not suffice**: in flight is about 640 MiB, the shelf keeps 64 MiB, the rest is freed to the allocator and stays resident as above |

## Predicted verdict

The hypothesis is false for (b) on both hosts with the plain system allocator, and the pool alone does not rescue it. A `doze-alloc`
crate is needed on Linux (the one `unsafe` call, `malloc_trim`) unless mimalloc or jemalloc is accepted; macOS needs mimalloc or a
bound on in-flight bytes. A bound on in-flight bytes (admission control: at most N MiB of request bodies held at once) is the
alternative that needs no `unsafe` and I expect to be the better design.

### Why macOS needs both numbers

The system allocator on macOS ends the burst at 810 MiB RSS and stays there, but the footprint the OS charges is 104 MiB: the rest are
pages marked reusable, which the kernel takes back under memory pressure and which Activity Monitor does not count. By that measure
the system allocator is the best of the four on macOS (mimalloc 400, jemalloc 657). I did not run a memory-pressure test to confirm
the kernel reclaims the reusable pages promptly, so the footprint figure is the OS's own accounting and not a measurement of what a
neighbouring process could use.

### Verdicts

1. **(a) holds**: a 1 GiB streamed upload costs at most a few MiB, on every allocator and both hosts.
2. **(b) fails with the plain system allocator on both hosts**, and by a wide margin on Linux: glibc keeps about 820 MiB of a 1,035 MiB
   peak, indefinitely. On macOS RSS fails the same way, but the OS footprint keeps +102 MiB, which is a smaller problem.
3. **The frame pool alone does not rescue it**; the peak was higher with it (982 against 810 on macOS, 1,273 against 1,035 on Linux; I did not find out why). It is the right tool for the
   kafka case (large frames, few in flight), the wrong one for many small bodies in flight at once.
4. **What does work, with the sizes found:**
   - *Linux, one `malloc_trim(0)` after the load has settled:* 823 to 3 MiB (baseline). It needs one `unsafe` call (`libc::malloc_trim`),
     so it needs the `doze-alloc` crate the plan already allows for. It must run when the server is quiet (after a burst, or on an idle timer).
   - *mimalloc as the global allocator on Linux:* 32 MiB after the burst without any `unsafe` in doze code (the unsafe is in the crate),
     +95 KB binary, a C dependency. On macOS it is worse than the system allocator by footprint.
   - *jemalloc:* only with a background purge thread configured; not worth it here (+324 KB, and the default retains everything).
   - *Admission control: a cap on request bodies in flight* (a semaphore taken before the body is read): with a cap of 256 the burst peaks at
     263 MiB RSS on macOS (footprint 18 MiB) against 810 (104), and on Linux (n=3000) at 96 MiB against 350. No `unsafe`, no new dependency.
     It does not make glibc give memory back (55 MiB retained at +10 s on Linux, 3 MiB after one trim) but it makes the amount to give back
     small. The cap is a *behaviour* (waiting requests wait on the connection), so its value is a design decision (kept in flight bytes).
5. **Recommendation for the plan:** (i) cap the request bodies in flight in the gateway (256 bodies of 64 KiB, 16 MiB, bounded the peak to 263 MiB RSS /
   96 MiB in these runs; the right default is a design decision, not measured here): it is the only measure that also bounds the *peak*, which matters on small machines; (ii) system allocator on macOS and Windows; (iii) on Linux either a `doze-alloc` crate with the one
   `malloc_trim(0)` call on a timer that fires only after the server has been idle for a few seconds, or mimalloc if a C dependency is acceptable;
   I would take the `doze-alloc` crate because it adds no binary size and the unsafe is one line with a stated reason. (iv) Do not use jemalloc.
   (v) Keep the frame pool for the large-frame case only (the kafka broker's).

### Caveats

One run per cell, no repeats, so run-to-run spread is unknown. Loopback only, one process, current-thread runtime; a multi-threaded runtime with per-thread
arenas would retain differently on glibc (the plan allows two workers). The 300 ms hold is a stand-in for real work. Windows was not tested.
