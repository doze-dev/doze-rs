doze core and CLI in Rust: the plan to finish

Status: proposed 2026-11-14, not approved. Owner's brief: "finish the real app and the real CLI in full… It's time to go for the entire finish." When this plan is done, doze is Rust end to end: engine and daemon, doze.hcl, the full CLI, every module, names and setup, the app. The Go product is then only an oracle.

Standing rules this plan obeys: the whole suite in Rust, no Go/Rust stitching (all-rust-no-go-stitching); ground-up Rust idioms, Go read for what, never for how (rust-port-write-it-in-rust); honest sizing; prior art and the file breakdown up front; a phase is done on evidence and an independent audit, not self-judged; Go is the floor, not the bar (modules plan D16).

Grounding (2026-11-14): doze at origin/main 23b73d6, doze-names 5ca25dc, doze-sdk efb28ba, doze-modules origin/main 6aa83d8 and its local pgext branch, doze-rs origin/main 2f1bb662 plus the open PR branches (cli-build #10, names-n4 #5, names-n6 #6, names-n5 #9, the app stack #8, #11 to #30), cli-design (the CLI proposal), app-plan (the app plan), the HCL spike report (_backup/spikes-2026-11-13/doze-hcl-spike.tgz), and four read-only surveys of the Go config, engine, control protocol and the doze-rs crates. Every Go line count below is wc -l of non-test .go files, with test lines after the slash.

2.3 The single binary

doze is one executable (crate doze-cli, src/main.rs). The dispatch is the first thing main does:

argv Runs Notes
doze __netd … doze_names::netd::run must be first, before clap, logging or tokio (Go's names.Helper() rule). The netd that dns-setup installs is a copy of the doze binary that ran setup (Go's model)
doze __daemon --config <abs> doze_daemon::run one daemon per project (Go: projects/<slug>/run/doze.admin.sock, doze.pid, doze.log)
doze __fetch … doze_fetch::child downloads in a child
doze (bare) terminal + GUI session → open Doze.app (execs doze-app); SSH → the dash (O2); piped → status the CLI proposal's three faces

Doze.app holds two binaries: doze (above) and doze-app (GPUI). The app plan's Q2 asks whether the app joins doze; it cannot under the 10 MB ceiling (the app alone is 12.1 to 15.6 MB), so this plan assumes two binaries (decision O1). Modules are separate binaries fetched from the registry, launched by doze-module-host over a socketpair (protocol 2).

Where names and netd fit: the daemon is the only writer of the zone for its stack (names plan); it takes leases through doze-bind for each instance and its twins, routes HTTP names at the front door, answers from its own live resolver before the registry (Go's ServeResolveIn), and records domains for trust. netd (macOS only) is the root-started tunnel daemon that drops to the user; it is the same doze binary run as __netd. On Linux and Windows there is no netd; services bind their own loopback addresses.

2.4 Compatibility at the seams (what must not change at cut-over)

  1. Control protocol 2, byte for byte. The app's doze-control client is tested against Go's frames; the Rust daemon must answer the same frames (state words reaped/booting/active/idle/crashing/failed/done, Go duration strings, nanosecond idle_timeout, snapshot on fall-behind). Contract 2's renames (asleep/waking/awake/dozing) are a protocol 3 change made in one commit across daemon, app and CLI, after cut-over (decision O3).
  2. The CLI's machine contract: --json envelopes (doze/v1), exit codes 0 1 2 4–9 130 (10 and 11 added), because the app runs doze -y up|down and doze --json doctor|lint|status as subprocesses.
  3. On-disk formats under DOZE_HOME and the project: project.json, run/ layout, journal.jsonl, log segments, .doze/state.json, doze.lock, names.json (format 2), data dirs clusters/<instance>. Kept so a person's data survives the switch and so Go and Rust can run side by side in the oracle (decision O3).
  4. Modules: Rust doze speaks only protocol 2. A doze.lock that pins protocol-1 (Go) module releases is re-resolved on the first up to the protocol-2 release of the same module (compat.md rules apply; nothing published breaks).

3. Order of work

Every phase starts with a behaviour catalogue for its area (docs/port/core/behaviours/<area>.md, distilled from the Go source, tests and docs; each item links to the Rust test or oracle case that holds it), ends with its gates green on the five targets where it applies, the size and weight gates green, and an independent audit (a separate agent, not the author) scoring it against the catalogue and the quality rules. Test diet (kafka plan rule 10) applies: no test per mutant.

Three tracks run in parallel from day one (the critical path, section 6, assumes three builders):

  • L (language): H1 → H2 → H3 → H4. The longest chain.
  • E (engine): E1 → E2 → D1 → D2, built against a Stack made in code, so it never waits for HCL.
  • M (modules): the modules plan's steps 9 to 15, against the module harness, so it never waits for the core.
  • The CLI (C1, C2) and privileged (P1) work joins where its inputs land.

3.2 The cut-over

When: after C2, D2, P1, M1 and M3 are done and audited. With three builders this is about day 95, or about day 83 with the two shortcuts in section 6.2.

Gates (all against the Rust binary, on macOS and Linux):

  1. test/integration: all 18 tests (DOZE_BIN, Rust modules).
  2. The app's 286-row real-daemon checklist with the Rust daemon and Rust CLI underneath: as many rows as Go (285).
  3. ground.ts: every command, flag and doze.hcl field the docs name exists.
  4. test/bench budgets; weight.md gates (section 6.3); zero leftover processes after every scenario.
  5. The owner's day: examples/shop and Larder up, used, slept, woken, down, on his Mac, with names and trust.
  6. An independent audit of the whole (not per phase): fidelity, quality rules, "nothing left behind".

Mechanics:

  • Doze.app bundles the Rust doze and doze-app. The app's doze-control client needs no change (2.4.1); its subprocess calls (doze -y up, --json doctor|lint|status) now hit the Rust CLI (2.4.2).
  • Homebrew formula and install.sh point at the Rust release; release tooling extends doze-module-release to doze.
  • Upgrade with a Go daemon running: Rust doze speaks protocol 2 to it, so doze update (and the first Rust up) asks the Go daemon to down, waits for its socket to go, and starts its own; data dirs, project.json, logs, journal and state are the same formats, so nothing is lost.
  • The machine switch on macOS: the Go netd launchd job (dev.doze.netd) is replaced by doze dns-setup once (one prompt).
  • doze.lock entries pinned to protocol-1 modules are re-resolved to protocol 2 on the first up.
  • The registry publishes protocol-2 module releases (they can go out before cut-over: Go selects only protocol 1).
  • Go is frozen: tagged, kept buildable as the oracle, no new behaviour.

Not gating cut-over (still in "the entire finish", built in parallel where a builder is free, section 6.2): M2 (postgres extensions), T (dash), W (Windows); then protocol 3 (Contract 2's state words) if O3 says so.

5. Privileged and DNS work

What needs root, once per machine, never per run (names plan): dns-setup (macOS: the netd launchd job and /etc/resolver/doze; Linux: doze0 with 192.0.2.53, the resolved or dnsmasq route, netd's systemd unit if any, the marked /etc/hosts block, the privileged-port sysctl; Windows: the NRPT rule to 127.0.0.53:53), trust (the machine CA into the keychain / ca-certificates / the Windows store; per-project domain routes; stale routes removed in the same prompt), and doctor --fix (runs whichever of the two the checks say is broken).

How it is built (P1), on what N4/N5 already have:

  • Each step is data (Step { check, apply, undo, says }, names plan); --check, --dry-run (aliases --print, --print-fix), the script and the app's "what will happen" sheet are all generated from the same list.
  • From the CLI: sudo from the terminal, one prompt for the whole script; each step reported separately.
  • From the app: Settings › Machine › Repair shows the plan (doze --json doctor --fix --dry-run), then runs doze doctor --fix behind one system admin prompt (privesc: osascript on macOS, pkexec on Linux, UAC on Windows). The app never runs anything privileged itself; it runs the CLI, so there is one code path.
  • doze-doctor adds the registry check (F5), the leftovers sweep (processes, sockets, routes, CA, data), and partial results that exit 11.
